## Перший запуск

Потрібні Python 3.12+, `uv`, SQLite FTS5; Node.js для JS-перевірок, Chromium для browser tests.

```bash
cd DevPost_htn
uv sync --frozen
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Для свіжої публічної копії створити `.env` за `.env.example`; приватну конфігурацію з архіву зберегти. Відкрити `http://127.0.0.1:8000`; API explorer — `/docs`, health — `/api/health`. Зупинка — Ctrl+C у власному терміналі. При зайнятому порту перевірити процес або вибрати `--port 8001`. Залишити localhost binding: production authentication/deployment не підготовлені.

Швидка перевірка без inference: імпортувати `synthetic_chat_a.json` → пошук → quote-only → оцінка → ручне збереження профілю → Markdown export. HTTP 404 для ще не створеного профілю очікуваний.

## Як працює застосунок

Telegram JSON нормалізується в chat-scoped SQLite зі збереженням оригінального тексту, source IDs і reply-зв'язків. FTS5 шукає лексично. API-аналітика обробляє збережені чанки, потім findings об'єднуються за рівнями. Є один власник job та bounded async pools для чанків і незалежних merge-вузлів.

Профіль створюється лише після успішної root-синтези. Власноруч редагований активний профіль захищено від автоматичного перезапису. Quote action повертає ID кандидата, сервер дістає точний текст зі своєї бази. Telegram додатково перевіряє allowlist, binding, trigger, cooldown і deduplication. Це не LoRA; окремі чати мають окрему пам'ять і профілі, а не окремі згенеровані застосунки.

## Реальна історія: активний запуск і recovery

`envelope_exceeded` — локальна межа payload, не вичерпання TPM. Будь-яка пара останніх чотирьох findings створює prompt 48 494–54 073 символи при batching-limit 38 000. Звичайний resume для цього error code прямо заборонений. Агент уже обійшов попередній стан та запустив нову спробу з компактнішою підказкою; підтримуваний і перевірений recovery endpoint для цього випадку ще треба прийняти. Не повторювати ручні зміни БД за цим описом.

Потрібні явне ущільнення/збіжна редукція і підтримуване відновлення того самого job. Зберегти chunks, придатні checkpoints, evidence і всі обліковані спроби. Якщо змінюється план batches, перевірити сумісність старого кешу. Не робити ручний SQL reset, новий імпорт або новий job для обходу блокування.

**Після виправлення й локальних тестів**, команда відновлення матиме такий вигляд:

```bash
PYTHONPATH=. \
MAX_IMPORT_SIZE_BYTES=167772160 \
ANALYSIS_CHUNK_SIZE=500 \
ANALYSIS_CONTEXT_OVERLAP=10 \
GEMINI_MAX_CALLS_PER_ANALYSIS=1000 \
GEMINI_ANALYSIS_CONCURRENCY=16 \
uv run python scripts/run_archive_analysis.py --run-analysis --concurrency 16
```

Поки job `running`, цю команду не запускати. Якщо envelope-помилка повториться, команда сама її не обходить. Runner повторно читає/ідемпотентно перевіряє приватний експорт і estimate. CLI default concurrency — 8, тому для 16 аргумент явний. Не запускати два runner або startup recovery сервера поряд з активним runner: recovery скидає claims, які вважає залишеними після рестарту.

1000 — lifetime cap спроб, не доларовий бюджет. Кодова default-конфігурація: 50 спроб, chunk size 50, upload bound 50 MiB; приватний запуск явно їх перевизначив. Concurrency не замінює RPM/TPM limiter. Usage у runner накопичується в поточному процесі; загального точного token/cost підсумку всіх рестартів немає. Не підвищувати cap автоматично.

## Окрема Telegram-група

1. Додати бота до окремої тестової групи й отримати саме її ID. Source ID у JSON не є дозволом на надсилання.
2. Записати ID у `TELEGRAM_ALLOWED_CHAT_IDS` локального `.env`.
3. У вкладці Telegram або через `PUT /api/telegram/bindings/{telegram_chat_id}` прив'язати потрібний локальний chat ID. Порожній allowlist блокує всі sends навіть за наявності binding.
4. Перезапустити відповідні процеси після зміни налаштувань.
5. Запустити один foreground poller:

```bash
uv run python -m app.telegram --once
# Або тривале опитування; зупинка Ctrl+C:
uv run python -m app.telegram
```

CLI приймає `--once`; опцій `--token`, `--group`, `--profile` немає. `--once` обмежує одним batch updates, не однією відповіддю. Перший погоджений тест — до трьох відповідей загалом на команди/згадки користувача; зупинити poller після тесту. Перевірити `/quote тема`, потім `/humor контекст` на завершеному профілі. Не запускати два poller на один токен.

`run_archive_analysis.py --telegram-check` містить setup-перевірку, але також спочатку читає приватний експорт. Setup marker допомагає знайти ID; сам не налаштовує allowlist/binding і не є round trip. Стікери та спонтанні вкиди поки вимкнені.

Поточний archive runner використовує timeout щонайменше 180 секунд; default застосунку — 30. Дочекатися явного завершення/зупинки поточного процесу та зафіксувати кінцевий стан перед пакуванням бази.

Тут незалежно пройшли 57 вибраних offline-тестів, включно з provider regressions, lint/format і JS syntax. Повна suite перевищила 30-секундний timeout, exit 124; причина не встановлена. Справжню browser-сесію і Telegram round trip під час передачі не повторювали. Попередні авторські звіти не замінюють незалежне приймання Task 04.

Приватний ZIP із ключами й реальною історією залишити для команди. `.gitignore` не очищає довільний архів. Для GitHub зробити **окрему чисту копію**: код, документація, lockfile, `.env.example`, синтетичні fixtures. Виключити `.env`, `data/`, приватний `result.json`, dumps, логи, приватні звіти та архіви. Перед першим commit перевірити staged contents і відсутність реальних секретів/повідомлень.

Scope/PRD/spec зараз у `devpost/`; перевірити розташування за остаточними вимогами форми. Відео 1–3 хвилини має показувати працюючий сценарій з дозволеними/синтетичними даними, без ключів і гуртожитської переписки. Опис/людські поля workflow заповнює команда, додати всіх трьох учасників і перевірити підтвердження подання та актуальний дедлайн.
